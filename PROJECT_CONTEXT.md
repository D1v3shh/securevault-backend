## 1. Project Purpose

SecureVault is the **backend for an enterprise secure file-sharing and device-trust platform**. It exists to let an organization:

- Onboard employee workstations through admin-issued **enrollment tokens**, issuing each device an **X.509 client certificate** signed by a HashiCorp Vault PKI intermediate CA.
- Allow the desktop client to log in **passwordlessly** by presenting that certificate (device fingerprint bound).
- Store files **encrypted at rest** using envelope encryption (per-file AES-256-GCM DEK wrapped by a Vault-held KEK).
- Share files user-to-user with expiry, permission levels, and enterprise controls (download caps, one-time access, device pinning).
- Enforce **RBAC** across five roles and record an **audit trail** of every security-relevant action.

This repository is **backend only**. There is no frontend in this workspace (see §5.6 for the sibling desktop app).

## 2. Architecture

Single NestJS 11 monolith, modular by feature, with provider interfaces at every infrastructure boundary so implementations can be swapped.

```
                       ┌─────────────────────────────┐
  SetupApp (Electron)  │  NestJS API  /api/v1        │
  Main desktop client ─▶  Helmet · CORS · Throttler  │
                       │  Global JwtAuthGuard        │
                       │  Global RolesGuard          │
                       │  ValidationPipe (whitelist) │
                       │  TransformInterceptor       │
                       │  GlobalExceptionFilter      │
                       └───┬────────┬──────────┬─────┘
                           │        │          │
                    MongoDB 7   Redis 7    Vault 1.15
                  (Mongoose 9)  (ioredis)  (KV + PKI + Transit)
                                              │
                                    Local disk ./storage/uploads
                                    (encrypted blobs)
```

### Request pipeline (order matters)

1. `helmet()`, `cookieParser()`, CORS (`src/main.ts`)
2. `ValidationPipe` — `whitelist: true`, `forbidNonWhitelisted: true`, error messages suppressed in production
3. Global guards, registered in `app.module.ts` via `APP_GUARD`: `JwtAuthGuard` → `RolesGuard` → `ThrottlerGuard`
4. Global interceptors: `LoggingInterceptor`, then `TransformInterceptor`
5. `GlobalExceptionFilter` catches everything

**Auth is deny-by-default.** Every route requires a JWT unless decorated `@Public()`.

### Response envelope

`TransformInterceptor` wraps every successful response:

```json
{ "statusCode": 200, "message": "Success", "data": { ... }, "timestamp": "..." }
```

Errors (from `GlobalExceptionFilter`):

```json
{ "statusCode": 403, "error": "Forbidden", "message": "...", "timestamp": "...", "path": "...", "method": "..." }
```

`GET /files/:id/download` bypasses the envelope — it writes the raw decrypted buffer via `@Res()`.

## 5. Major Features and Flows

### 5.1 Password login → tokens

`POST /api/v1/auth/login` (public, throttled 5/60s) → `AuthService.login()`

1. `usersService.findByEmail` (lowercased, `deletedAt: null`)
2. Reject if `!isActive` (403) or account locked (403)
3. `bcrypt.compare`; on failure `recordLoginAttempt(false)` → increments `failedLoginAttempts`, locks for **30 min** at **5** attempts (`APP_CONSTANTS`)
4. On success reset counters, stamp `lastLoginAt` / `lastLoginIp`
5. `generateTokens()` — access JWT (`type: 'access'`, 15m default) + refresh JWT (`type: 'refresh'`, 7d), signed with **separate secrets**
6. `storeRefreshToken()` — SHA-256 hash of the JWT stored in `refresh_tokens` (raw token never persisted)
7. `sessionsService.createSession({ authMethod: 'password', deviceId: PASSWORD_SESSION_DEVICE_ID })` — one active password session per user; a new password login supersedes the previous one
8. Audit `LOGIN_SUCCESS`; every rejection branch above audits `LOGIN_FAILURE` with the reason in metadata while the response stays generic
9. Returns tokens, `sessionId`, plus `mustChangePassword` / `isFirstLogin` flags

`POST /auth/refresh` (public, throttled 10/60s) is guarded by `JwtRefreshGuard`, which verifies the refresh token's signature (separate secret), `exp` and `type === 'refresh'` before the handler runs. `AuthService.refreshTokens` then looks the SHA-256 hash up in `refresh_tokens`, rotates it, re-checks `isActive`, and audits `TOKEN_REFRESH`. Presenting an already-rotated token revokes **every** refresh token for that user and audits `SUSPICIOUS_ACTIVITY`, returning the same generic 401.

Every authenticated request: `JwtStrategy.validate()` rejects non-`access` tokens, then checks Redis key `sv:bl:token:<jwt>`; if present → 401 "Token has been revoked". Request gets `req.user = { userId, uuid, email, role }`.

### 5.2 Device enrollment (SetupApp flow)

```
Admin: POST /admin/create-enrollment-token   (ADMIN|SUPER_ADMIN)
   └─ enr_<64 hex>, bound to userId + employeeId, expiresInHours (default 24), maxDevices (default 1)

Device: POST /setup/verify-token   (public)  → validity, remainingDevices, expiresAt
Device: POST /setup/enroll         (public, 5/60s)
   1. verifyToken()  — expiry, usedCount < maxDevices, employeeId match, user active
   2. CertificateUtil.isValidCsrPem(csr)                       → 400 if malformed
   3. Duplicate fingerprint check → BLOCKED = 400, APPROVED = 409
   4. devicesService.registerDevice()  → status PENDING
   5. devicesService.approveDevice()   → APPROVED, approvedBy 'system:enrollment'
   6. certificatesService.signAndStoreCertificate()
        CN = <employeeId>.<deviceId>.securevault.local, ttl 8760h
        VaultPkiService.signCsr → pki_int/sign/securevault-device
        persists certificate + csr PEM, SHA-256 fingerprint, validity window
        devicesService.bindCertificate(deviceId, serial)
   7. Consume token (usedCount++, record fingerprint + IP, isUsed when exhausted)
   8. Audit: DEVICE_ENROLLMENT
   → { certificate, serialNumber, issuingCa, caChain, deviceId, validFrom, validTo }
```

**Enrollment auto-approves the device.** The token is treated as the admin's trust decision; there is no separate approval step in this path.

### 5.3 Certificate login (passwordless)

`POST /api/v1/auth/certificate-login` (public, 10/60s) → `certificateLogin()`

`CertificatesService.verifyCertificate()` runs ten checks in order: PEM format → parse via `crypto.X509Certificate` → `validTo` → `validFrom` → lookup by serial (falls back to a **full-collection scan with normalized serial comparison**) → `status !== REVOKED` → no row in `certificate_revocations` → device fingerprint matches the stored binding → `devicesService.isDeviceTrusted(fingerprint)` (must be `APPROVED`) → stored SHA-256 fingerprint matches recomputed.

Chain verification against the intermediate CA is attempted but **failures only log a warning** — deliberately soft so mock dev certificates pass. Comment in source says this must become a hard failure in production.

On success: issue JWTs → store hashed refresh token → `sessionsService.createSession(authMethod: 'certificate')` (ends prior sessions for that device) → `devicesService.updateLastSeen` → audit `CERT_LOGIN_SUCCESS`.
On failure: audit `CERT_LOGIN_FAILURE`, plus `REVOKED_CERT_LOGIN` or `FINGERPRINT_MISMATCH` security events, then 401.

### 5.4 File upload / download (envelope encryption)

**KEK initialization** (`EncryptionService.onModuleInit`): read `secret/data/securevault/master-encryption-key` from Vault → if absent and Vault healthy, generate 32 random bytes and write it → otherwise **fall back to `sha256(JWT_ACCESS_SECRET)`** with a loud warning.

Upload — `POST /files/upload` (multipart, `FileInterceptor('file')`, 100 MB cap in both Multer and `ParseFilePipe`):

1. MIME allow-list check (`APP_CONSTANTS.ALLOWED_MIME_TYPES`, 21 types) → 400
2. SHA-256 checksum of the **plaintext** buffer
3. `generateKey()` → fresh DEK; `encryptKey()` wraps it as `[iv(16)][authTag(16)][ciphertext]`; encrypted DEK also mirrored into Vault at `securevault/file-keys/<keyId>`
4. `encrypt(buffer, dek)` → AES-256-GCM
5. Storage path `YYYY/MM/DD/<uuid><ext>`; encrypted bytes written to disk
6. Mongo `files` doc holds `encryptedDek`, `encryptionIv`, `encryptionAuthTag` (all hex), checksum, `accessLevel`
7. Audit `FILE_UPLOAD`

Download — `GET /files/:id/download`: access check → read blob → `decryptKey` → `decrypt` → **recompute SHA-256 and compare to stored checksum**; mismatch → 400 "File integrity check failed" → audit `FILE_DOWNLOAD` → stream with `Content-Disposition: attachment`, `no-store`, `nosniff`.

The whole file is buffered in memory on both paths (twice on download: ciphertext + plaintext). `downloadStream` exists on the provider but is unused and cannot be adopted without changing the integrity design — §10.5.

**File access control** (`findFileWithAccessCheck`, resolves by `uuid` first then `_id`) — evaluated in this order:

1. **Owner or ADMIN/SUPER_ADMIN → allowed**, before any share lookup.
2. The file's own `accessLevel`:

   | accessLevel | Who else can read |
   |---|---|
   | `private` | nobody (falls through to step 3) |
   | `department` | MANAGER |
   | `internal`, `public` | any authenticated user |

3. Otherwise `FileAccessValidationService.validateAccess(file._id, userId, action)` — an ACTIVE `file_access` grant, which also enforces lazy expiry, permission level (`VIEW` for metadata, `DOWNLOAD` for the blob), download caps and device pinning. No usable grant → 403.

Delete and any `ownerOrAdminOnly` operation: owner or ADMIN/SUPER_ADMIN only, no share path. Delete is **soft** (`isDeleted`, `deletedAt`, `deletedBy`); the blob stays on disk until `scripts/cleanup-expired-files.ts` purges it after 30 days.

### 5.5 File sharing

`POST /shares` → `ShareService.shareFile()` validates: file exists and not deleted → **requester owns the file (read from DB, never trusted from the request)** → target user exists, not soft-deleted, active → not self → `expiresAt` parses and is in the future → no existing ACTIVE share for the same (file, user). A partial unique index on `{fileId, sharedWithUserId, status}` filtered to `ACTIVE` enforces the last rule at the database level too.

`DELETE /shares/:shareId` — owner only, sets `REVOKED`.
`GET /shares/shared-with-me`, `GET /shares/shared-by-me` — paginated, default filter `status = ACTIVE`, sortable by `createdAt` / `expiresAt`; `search` switches to an aggregation pipeline that `$lookup`s `files` and re-fetches each row to populate.
`GET /shares/:shareId` — owner or recipient only.

Permission model (`SharePermission` VIEW 10 < DOWNLOAD 20 < EDIT 30 < FULL_ACCESS 100; `ShareAction` maps DELETE and SHARE to FULL_ACCESS).

`FileAccessValidationService` implements the enforcement side: active-share lookup, **lazy expiration** (flips `ACTIVE`→`EXPIRED` on access and audits it), permission check, download-cap check, device-certificate pinning, plus `recordDownload()` (one-time access → `REVOKED`; cap reached → `EXPIRED`) and `expireOverdueShares()` for a future scheduled job.

> ⚠ **This service is never called.** `FilesService.downloadFile` does not consult shares. See §10.2.

### 6.3 RBAC

`Role` enum with `ROLE_HIERARCHY` weights: `SUPER_ADMIN` 100 → `ADMIN` 80 → `MANAGER` 60 → `EMPLOYEE` 40 → `VIEWER` 20.

Two independent mechanisms:

- **`RolesGuard`** — plain `requiredRoles.includes(user.role)`, **exact match, no hierarchy**. `@Roles(ADMIN)` does *not* admit `SUPER_ADMIN`. Every existing admin route lists both explicitly, so this is currently correct but is a trap for new routes.
- **`AdminService.validateRoleChange`** — *does* use `ROLE_HIERARCHY`: an admin may only assign a role strictly below their own. Plus guards against self-deactivation and self-role-change, and role changes are SUPER_ADMIN-only.

`Permission` enum + `ROLE_PERMISSIONS` matrix and `PermissionsService` exist but **nothing calls them**; `hasHigherOrEqualRole`, `ADMIN_ROLES`, `USER_MANAGEMENT_ROLES` are also unused. This is deliberate debt, not an oversight — §10.2 lists the access boundaries a permission-based swap would move.

## 7. Configuration / Setup

### 7.1 Environment variables

`ConfigModule.forRoot({ isGlobal: true, load: configModules, validate: validateEnv, expandVariables: true })`. The Zod schema in `src/config/env.validation.ts` runs at boot and **throws with a field-by-field report** on failure. All values arrive as strings and are parsed inside the `registerAs` factories.

Required with no default: **`MONGODB_URI`**, **`JWT_ACCESS_SECRET`** (min 32 chars), **`JWT_REFRESH_SECRET`** (min 32 chars).

Groups (see `.env.example` for the full template): app (`NODE_ENV`, `APP_PORT` 3000, `APP_HOST` 0.0.0.0, `API_PREFIX` api/v1, `APP_CORS_ORIGINS` comma-separated) · mongo · redis (`REDIS_KEY_PREFIX` default `sv:`) · jwt (`15m` / `7d`) · vault (`VAULT_ENABLED`, `VAULT_ADDR`, `VAULT_TOKEN`, `VAULT_MOUNT_PATH` secret, `VAULT_SECRETS_PATH` securevault, `VAULT_TRANSIT_ENGINE`, retry) · vault PKI (`VAULT_PKI_PATH` pki_int, `VAULT_PKI_ROLE` securevault-device) · storage (`STORAGE_TYPE` local, paths, 100 MB) · encryption (`aes-256-gcm`, key 32, **IV 16**, tag 16) · rate limit (`RATE_LIMIT_TTL` 60, `RATE_LIMIT_MAX` 100; the `*_AUTH_*` vars are validated but **never read** — per-endpoint limits are hardcoded in `@Throttle` decorators) · logging · `SEED_SUPER_ADMIN_*` · `BULL_QUEUE_PREFIX` (unused).

Config namespaces read by key path: `app.*`, `database.*`, `jwt.*`, `redis.*`, `vault.*`, `storage.*`. Some services read **raw env names** instead (`VAULT_PKI_PATH`, `ENCRYPTION_*`, `RATE_LIMIT_*`, `REDIS_KEY_PREFIX`) — both styles work because Zod's parsed output is merged into the config source.

```bash

cp .env.example .env                       # then set the two JWT secrets (32+ chars each)
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # run twice

```

## 9. Security Considerations

**Implemented and verified**

- bcrypt 12 rounds; password complexity enforced on change (`@Matches` upper + lower + digit + special)
- Separate access/refresh secrets, distinct `type` claim, rejected if swapped
- Refresh tokens stored **SHA-256 hashed**; rotation on every refresh (old row `isRevoked = true`); TTL index cleans up
- Access-token blacklist in Redis with TTL equal to remaining token life; checked on every request in `JwtStrategy`
- Password change / reset / deactivation revoke **all** refresh tokens for that user
- Account lockout: 5 failures → 30 minutes; auto-clears on expiry
- Envelope encryption: per-file random DEK, AES-256-GCM with auth tag, KEK from Vault
- Post-decryption checksum verification (tamper/corruption detection)
- Path-traversal guard in `LocalStorageProvider.getFullPath`; `FileUtil.sanitizeFilename` strips to `[a-zA-Z0-9.\-_]`
- MIME allow-list, 100 MB cap
- Regex-injection escaping on every user-supplied search term (users, files, devices, shares)
- `ValidationPipe` with `whitelist` + `forbidNonWhitelisted`; error messages suppressed in production
- Helmet, explicit CORS origin list, `GlobalExceptionFilter` never leaks stacks outside development
- Share creation reads ownership from the database, never from the request body
- Audit log is append-only in practice (no update paths); `CryptoUtil.secureCompare` available for constant-time comparison

**Gaps and risks**

1. **`POST /setup/generate-certificate` is `@Public()` and signs arbitrary CSRs with no enrollment token and no authentication.** Only a 3/60s throttle stands in front of it. It also passes `userId: 'system'` into `new Types.ObjectId('system')`, which throws `BSONError` — verified — so it returns 500 rather than issuing a certificate. It is a latent unauthenticated certificate-issuance endpoint. Remove it or gate it behind `@Roles(SUPER_ADMIN, ADMIN)`.
2. **Certificate chain verification is advisory.** `verifyCertificate` step 10 logs a warning and continues when `verify()` fails. With `VAULT_ENABLED=false` the PKI service returns fake PEM "certificates" that `crypto.X509Certificate` cannot even parse, so `parseCertificate` returns null and login fails — meaning **certificate login only works with Vault enabled**. Before production, make chain failure a hard 401.
3. **KEK fallback derives the master key from `JWT_ACCESS_SECRET`** when Vault is unavailable. Files encrypted under the fallback key become undecryptable once Vault comes online (and vice versa), and rotating the JWT secret would destroy them. Never allow this path in production.
4. **`VaultService` uses a static root token** from env. No AppRole, no token renewal, no lease handling.
5. **AES-GCM IV is 16 bytes** (`ENCRYPTION_IV_LENGTH=16`) rather than the recommended 12. Functional, slightly off-spec. Changing it would break decryption of existing files.
6. **`.env.production.example` contains real-looking secrets** — two concrete 64-hex JWT secrets, a personal email, and a plaintext password (`DiKu@671`). It is currently **untracked** (`git status` shows `??`). Do not commit it; rotate those values.
7. **No `trust proxy`** → IP-based audit trails and throttling are wrong behind a load balancer.
8. **Files are fully buffered in memory** on upload and download; a few concurrent 100 MB transfers can exhaust the heap.
9. **`GET /devices/:id` has no ownership or role check** — any authenticated user can read any device's fingerprint, MAC, serial, and certificate serial by ID.
10. **`GET /files/:id/download` is not rate limited** beyond the global 100/60s, and `accessLevel: internal`/`public` files are readable by every authenticated user including `VIEWER`.
11. **Audit logs have no retention policy** — the TTL index is commented out and no export path exists.
12. Logout ends **all** the user's sessions across every device, not just the current one.

### 10.5 Security items worth a dedicated pass

Ranked. The first two outrank everything else in §10.

1. **Certificate login has no proof of private-key possession.** `CertificateLoginDto` takes `certificate` + `deviceFingerprint` and no challenge or signature. The integrity check is `sha256(presented PEM)` compared to the stored fingerprint — but the PEM is public data, so anyone holding a copy of a user's certificate and their device fingerprint can authenticate as that user. Fixing this needs a signed-nonce exchange, which is a client protocol change.
2. **Chain verification is soft-failed.** `CertificatesService.verifyCertificate` step 10 logs "In production, this should be a hard failure" and then returns `valid: true` anyway. Do not flip it without checking `VAULT_ENABLED` in the target environment (rule 23) — with Vault disabled the mock CA PEMs fail every chain check and would lock out all certificate logins.
3. **CSR-to-certificate key binding is unverified.** The old always-true stub was deleted rather than implemented. Node has no PKCS#10 API (`crypto.X509Certificate` covers the cert side; `createPublicKey` rejects CSR PEMs), so a real check needs `@peculiar/x509` (`Pkcs10CertificateRequest`) or `node-forge`. `csrPem` *is* stored on the certificate row, so the comparison is possible. Note Vault PKI already binds the issued certificate to the CSR's public key when it signs, so this is defence-in-depth at issue time — it only becomes load-bearing if certificate PEMs can enter the system by a path other than `signAndStoreCertificate`.
4. **Streaming downloads vs. integrity.** `downloadStream` cannot be used as designed: the GCM auth tag covers the whole file and is only verified at `decipher.final()`, and the SHA-256 check runs over the entire plaintext — both *after* every byte would already have been streamed to the client. The current guarantee is "no byte leaves until the whole file verifies". Streaming requires either accepting verify-after-delivery with a destroyed socket on failure, or moving to chunked/framed AEAD, which changes `encryptionIv`/`encryptionAuthTag`/`checksum` to per-chunk values and needs migration of existing files. Both paths also buffer the file twice in memory today (ciphertext + plaintext).

## 11. MUST KNOW / DO NOT BREAK

Rules for anyone — human or agent — changing this codebase.

### Cryptography and data integrity

1. **Never change `ENCRYPTION_ALGORITHM`, `ENCRYPTION_KEY_LENGTH`, `ENCRYPTION_IV_LENGTH`, or `ENCRYPTION_AUTH_TAG_LENGTH` on a system with existing files.** `decryptKey` slices the packed blob at fixed offsets `[iv(16)][authTag(16)][ciphertext]`; changing lengths makes every stored DEK — and therefore every file — permanently unreadable.
2. **Never change how the master KEK is derived or where it is stored** without a migration that re-wraps every `encryptedDek` in the `files` collection. Rotating `JWT_ACCESS_SECRET` while the Vault fallback path is in use destroys all file data.
3. **`EncryptionService.rotateKey()` only replaces the in-memory KEK and the Vault copy — it does NOT re-encrypt existing DEKs**, despite the docstring. Calling it in production orphans every existing file. Do not call it until re-wrapping is implemented.
4. **Keep the post-decryption checksum comparison** in `downloadFile`. It is the only tamper/corruption detection in the system.
5. **Never store a raw refresh token.** Always `sha256(token)` before writing to or reading from `refresh_tokens`.
5b. **`scripts/cleanup-expired-files.ts` is irreversible.** It deletes the blob *and* the metadata row holding `encryptedDek` / `encryptionIv` / `encryptionAuthTag`, so a purged file cannot be decrypted even if the ciphertext is restored from a backup. Keep the three safeguards: `dryRun` is a required argument (no default), every purge writes its audit row *before* the delete, and runs are capped by `limit`. Always dry-run first — `--confirm` is what actually deletes.

### Auth and authorization

6. **`JwtAuthGuard` is global.** Adding a controller automatically protects it. Adding `@Public()` removes *all* authentication — justify every use.
7. **Keep the `payload.type` check** in both JWT strategies. Without it a refresh token becomes a valid access token.
8. **Keep the Redis blacklist check** in `JwtStrategy.validate`. Removing it makes logout cosmetic.
8b. **`/auth/refresh` must keep both `@Public()` and `@UseGuards(JwtRefreshGuard)`.** Global guards run before route guards, so dropping `@Public()` makes the endpoint demand an access token and breaks refresh entirely; dropping the route guard removes the only signature / `exp` / `type` verification of the refresh token, since the service just matches a SHA-256 hash.
8c. **Keep refresh-token re-use detection.** `refreshTokens` deliberately fetches revoked rows too: a token presented after rotation revokes the user's whole token set. Filtering on `isRevoked: false` in the lookup would silently restore the old behaviour where a leaked token is indistinguishable from an unknown one. Keep the failure message identical across all rejection branches.
9. **`RolesGuard` is exact-match, not hierarchical.** Always list every permitted role: `@Roles(Role.SUPER_ADMIN, Role.ADMIN)`. If you convert it to hierarchical matching, audit every existing `@Roles` decorator first.
10. **Never trust client-supplied ownership or identity.** `ShareService.shareFile` deliberately loads the file and compares `uploadedBy` against `req.user.userId`. `FilesService.findFileWithAccessCheck` is the single access gate for files — route all new file operations through it.
11. **Preserve the self-protection checks** in `AdminService`: no self-deactivation, no self-role-change, and `validateRoleChange`'s strict "below your own level" rule.

### Data model

12. **Soft deletes:** users use `deletedAt`, files use `isDeleted`. Every query must filter accordingly — `UsersService` uses `deletedAt: null`, `FilesService` uses `isDeleted: false`. Omitting the filter leaks deleted records.
13. **Do not update or delete `audit_logs` or `certificate_revocations`.** Both are append-only by design.
14. **Do not drop the partial unique index** on `file_access` (`{fileId, sharedWithUserId, status}` where `status = ACTIVE`) — it is the last line of defence against duplicate shares.
15. **`autoIndex` is off in production.** Any new index must be created explicitly during deployment.
16. IDs are dual-keyed: `files`, `devices`, `certificates`, and `sessions` each have a business UUID *and* a Mongo `_id`, and several lookups try both. Keep the `try { findById } catch {}` pattern when adding resolvers — an invalid ObjectId string throws.

16b. **Audit `action` values come from the `AuditAction` enum, never from request data.** `AuditService.findAll` filters on those values, and the admin audit API is the consumer. An interceptor deriving actions from URLs was removed for exactly this reason — do not reintroduce a parallel taxonomy.
16c. **Audit failure branches too, but keep responses generic.** `LOGIN_FAILURE` records *why* in `metadata.reason` while the HTTP response stays a plain "Invalid credentials", so the audit trail is useful without enabling account enumeration.

### Process

17. **Never commit `.env` or `.env.production.example`.** The latter currently contains real secrets and is untracked — keep it that way.
18. **`npm run lint` runs `eslint --fix` and rewrites source files.** Use `npx eslint <paths>` (no `--fix`) when you only want to inspect.
19. **`npm run build` deletes `dist/` before compiling** (`nest-cli.json` sets `deleteOutDir: true`), so a failed build leaves no output. `dist/` is gitignored and no longer ahead of `src/`. Keep `"scripts"` in `tsconfig.build.json`'s `exclude` — without it TypeScript raises the inferred `rootDir` and emits `dist/src/main.js`, which breaks both `start:prod` and the Dockerfile.
20. **Keep `app.useLogger()` in `main.ts`.** `bufferLogs: true` holds startup logs until a logger is attached; removing the `useLogger` call silently reverts to the default console logger and makes `LOG_LEVEL` / `LOG_DIR` inert again.
21. **Env changes go in two places:** the Zod schema in `src/config/env.validation.ts` *and* the relevant `src/config/*.config.ts` factory. The app will refuse to boot on an unrecognised-but-invalid value, and a variable missing from the schema is silently unavailable.
22. **Vault dev mode loses all data on container restart.** After `docker compose down -v`, re-run `npx ts-node scripts/setup-vault-pki.ts` or certificate signing and KEK loading will fall back to mock/derived values.
23. **Do not "fix" `verifyCertificate` step 10 into a hard failure without checking `VAULT_ENABLED`** in the target environment — with Vault disabled the mock CA PEMs will fail every chain check and lock out all certificate logins.
24. **Preserve the access-check ordering in `FilesService.findFileWithAccessCheck`:** owner and ADMIN/SUPER_ADMIN pass through *before* any share lookup → then the file's own `accessLevel` rules → then `FileAccessValidationService.validateAccess`. Reordering either grants access the accessLevel table does not, or floods the audit trail with false `access_denied` rows for files that are readable anyway.
25. **`recordDownload()` runs only after the bytes are delivered.** `downloadFile` returns the authorizing share instead of consuming quota; the controller calls `recordShareDownload` from `res.once('finish')`, which does not fire on an aborted transfer. Never move it into the service — a failed download would burn a one-time share.
26. **`serialNumberNormalized` is derived by the schema hook, never set by hand.** It must stay identical to `CertificateUtil.normalizeSerialNumber`; a test pins the two together. The index is intentionally non-unique — `serialNumber` already carries uniqueness, and a unique index would reject the nulls on pre-backfill rows.
